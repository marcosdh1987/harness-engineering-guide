# Use and Modify Existing Skills

Most value comes before you ever author a skill: learn to *run* the ones a repo already
ships, and to *change* them safely.

## What a skill is here

A skill packages a repeatable engineering task with explicit input and structured output,
so Claude performs it consistently instead of improvising. For the conceptual framing see
[Skills vs Prompts](../concepts/skills-vs-prompts.md) and
[Patterns › Skill Design](../patterns/skill-design.md) — this page is about the mechanics.

## Internal vs. external vs. projected

Three locations, and only one is yours to edit:

| Type | Location | Edit here? | Comes from |
|---|---|---|---|
| Internal | `.github/skills/<name>.md` | **Yes** | Hand-authored (source of truth) |
| External | `.github/skills-external/<name>/SKILL.md` | No | Installers + `make sync-skills` |
| Projected | `.claude/skills/<name>/SKILL.md` | No (overwritten) | Generated by the sync engine (a symlink to the source) |

!!! warning "Edit the source, never the projection"
    `.claude/skills/` is generated output (symlinks back to the source). If you change a
    projected copy, the change is fragile and will be overwritten on the next sync — and it
    won't reach the other tool adapters. Always edit `.github/skills/<name>.md`.

## Using a skill in a session

Claude discovers skills from `.claude/skills/`, matching your request against each skill's
`description`. To browse what a repo actually ships, read the live inventory on
[Reference › Skills](../reference-implementation/ml-python-base/skills.md), then ask Claude
to perform a task that a skill covers and let it drive.

## Modifying an internal skill safely

1. Open the source: `.github/skills/<name>.md`.
2. Edit the `description` (its trigger) and/or the body (`Purpose` / `Required Input` /
   `Output Format` / `Execution Rules`).
3. Re-project it with `make sync-skills` (see [Create Your First Skill](create-your-first-skill.md)
   for the full flow).
4. Confirm nothing drifted with `make check-sync`.

Never edit the projected copy or an external skill; see
[Reference › Drift Control](../reference-implementation/ml-python-base/drift-control.md)
for why the harness enforces this.

## `context: fork` and `allowed-tools` in practice

Two native skill-frontmatter fields are worth knowing early:

!!! note "Native Claude Code capability"
    - **`context: fork`** runs the skill in an isolated subagent, so a high-output task
      (like exploring a large codebase) doesn't flood your main conversation's context.
    - **`allowed-tools`** restricts which tools a skill may use — e.g. read-only, to
      prevent accidental destructive edits.

!!! tip "How ml-python-base applies it"
    Internal skills keep minimal frontmatter, so these fields aren't set on them by
    default. The [Tools › Claude Code](../tools/claude-code.md) page documents
    `context: fork`, `allowed-tools`, and `argument-hint` for when you want them.

## Mini study flow

1. Read the [skills inventory](../reference-implementation/ml-python-base/skills.md) and pick one.
2. Run a task it covers; observe how it structures the work.
3. Tweak its source `description` or a rule; `make sync-skills`; re-run.
4. Verify with `make check-sync`. Then author your own → [Create Your First Skill](create-your-first-skill.md).
